# Environment files and configuration

Guide for a developer who starts working on `eionet2-dashboard`. It explains which `.env` files exist, who reads them, which variables actually matter, and how to get a local environment running.

This is about **build/runtime configuration**. Application content configuration (texts, list ids, tooltips stored in the SharePoint configuration list) is documented separately in [CONFIGURATION.md](/home/mihai.nicolae/projects/edw/eea/eionet2-dashboard/CONFIGURATION.md).

---

## 1. The three configuration layers

The project is a Microsoft Teams app scaffolded with **Teams Toolkit (TeamsFx v5)**. It has two deployable parts (`tabs/` = React/CRA frontend, `api/` = Azure Functions backend) and therefore three distinct layers of environment files, each with a different consumer.

| Layer | Files | Read by | Written by |
|---|---|---|---|
| 1. Toolkit / provisioning state | `env/.env.<envName>`, `env/.env.<envName>.user` | `teamsfx` CLI and the Teams Toolkit VS Code extension, while running provision / deploy / publish. Values are substituted into `teamsapp.yml`, `appPackage/manifest.json`, `aad.manifest.json`, `templates/azure/*` | Mostly **machine generated**. The toolkit writes provision outputs back into these files |
| 2. Frontend build config | `tabs/.env.teamsfx.<envName>` | `env-cmd` inside the `tabs` npm scripts (`dev:teamsfx`, `build:teamsfx`). Values are baked into the JS bundle at build time by CRA | `.local` is generated by `teamsapp.local.yml`; `.dev` and `.Prod_EEA` are **maintained by hand** |
| 3. Backend local runtime config | `api/.env.teamsfx.local`, `api/local.settings.json` | `env-cmd` + the Azure Functions host, only when running the API locally | `.env.teamsfx.local` is partially generated by `teamsapp.local.yml`, the rest is by hand |

In the cloud there is no layer 3: the Function App reads its values from **Azure App Settings**, provisioned by `templates/azure/teamsFx/function.bicep`.

All these files are gitignored (`.gitignore` lines for `env/*`, `.env.teamsfx.local`, `.env.teamsfx.dev`, `.env.teamsfx.Prod_EEA`), so nothing arrives with a fresh clone. You have to obtain or generate them.

## 3. Variables that the code actually reads

This is the short list that matters. Everything else in the env files is toolkit bookkeeping.

### 3.1 Frontend (`tabs/`, build-time, must be prefixed `REACT_APP_`)

| Variable | Used in | Meaning |
|---|---|---|
| `REACT_APP_FUNC_ENDPOINT` | [apiProvider.js:14](/home/mihai.nicolae/projects/edw/eea/eionet2-dashboard/tabs/src/data/apiProvider.js#L14) | Base URL of the Azure Functions API. All calls go to `<endpoint>/api/<command>` |
| `REACT_APP_SHAREPOINT_SITE_ID` | [apiProvider.js:100](/home/mihai.nicolae/projects/edw/eea/eionet2-dashboard/tabs/src/data/apiProvider.js#L100) | Graph site id of the SharePoint site holding the app data |
| `REACT_APP_CONFIGURATION_LIST_ID` | [apiProvider.js:101](/home/mihai.nicolae/projects/edw/eea/eionet2-dashboard/tabs/src/data/apiProvider.js#L101) | Id of the SharePoint configuration list (see CONFIGURATION.md) |
| `REACT_APP_INSIGHTS_CONNECTION` | [appInsights.js:7](/home/mihai.nicolae/projects/edw/eea/eionet2-dashboard/tabs/src/data/appInsights.js#L7) | Application Insights connection string. If empty, telemetry is simply not initialised |
| `REACT_APP_VERSION` | [Tab.jsx:113](/home/mihai.nicolae/projects/edw/eea/eionet2-dashboard/tabs/src/components/Tab.jsx#L113), [BottomMenu.jsx:174](/home/mihai.nicolae/projects/edw/eea/eionet2-dashboard/tabs/src/components/BottomMenu.jsx#L174) | **Not** set in any env file. Injected by the `start` / `build` npm scripts from `$npm_package_version` |

Local development also needs the CRA dev-server variables, which the toolkit writes into `tabs/.env.teamsfx.local`: `BROWSER=none`, `HTTPS=true`, `PORT=53000`, `SSL_CRT_FILE`, `SSL_KEY_FILE`.

### 3.2 Backend (`api/`, runtime)

| Variable | Used in | Meaning |
|---|---|---|
| `M365_TENANT_ID`, `M365_CLIENT_ID`, `M365_CLIENT_SECRET` | [getGraphData/index.js:45-47](/home/mihai.nicolae/projects/edw/eea/eionet2-dashboard/api/getGraphData/index.js#L45-L47) | AAD app credentials for the on-behalf-of / app-only Graph calls. The function returns HTTP 500 with `Missing required M365_* configuration for OBO.` if any is missing |
| `M365_AUTHORITY_HOST` | [getGraphData/index.js:48](/home/mihai.nicolae/projects/edw/eea/eionet2-dashboard/api/getGraphData/index.js#L48) | Optional, defaults to `https://login.microsoftonline.com` |
| `GRAPH_SCOPES` | [getGraphData/index.js:49](/home/mihai.nicolae/projects/edw/eea/eionet2-dashboard/api/getGraphData/index.js#L49) | Optional, comma or space separated. Defaults to `https://graph.microsoft.com/.default`. Not present in any env file |
| `REACT_APP_REPORTNET3_KEY` | [getReportingData/index.js:10](/home/mihai.nicolae/projects/edw/eea/eionet2-dashboard/api/getReportingData/index.js#L10) | Reportnet 3 API authorization key. The `REACT_APP_` prefix is misleading, this is a **server-side secret**, it is never used by the frontend |
| `FUNCTIONS_WORKER_RUNTIME`, `AzureWebJobsStorage` | Azure Functions host | Standard Functions host settings, also present in `api/local.settings.json` |

`ALLOWED_APP_IDS`, `M365_APPLICATION_ID_URI` and `API_ENDPOINT` are set by the toolkit and by `function.bicep`, but no application code reads them. `SQL_ENDPOINT`, `SQL_DATABASE_NAME`, `SQL_USER_NAME`, `SQL_PASSWORD` in `api/.env.teamsfx.local` are empty scaffolding leftovers.

### 3.3 Cloud gap to be aware of

`function.bicep` provisions `API_ENDPOINT`, `ALLOWED_APP_IDS`, `M365_*` and `IDENTITY_ID` as Function App app settings, but **not** `REACT_APP_REPORTNET3_KEY`. In `dev` and `Prod_EEA` that key must be set manually as an application setting on the Function App, otherwise the reporting tab silently gets an empty key. Because the bicep merges with `currentAppSettings`, a manually added setting survives re-provisioning.

### 3.4 Dead variables still present in the env files

These are leftovers from the original TeamsFx scaffold and from the auth simplification (commit `d1866bb`, "chore: simplify auth"). No code reads them. Authentication now goes through the Teams JS SSO (`authentication.getAuthToken()`), and `tabs/public/auth-start.html` / `auth-end.html` receive the client id as a URL query parameter, not from the build.

- `REACT_APP_CLIENT_ID`
- `REACT_APP_START_LOGIN_PAGE_URL`
- `REACT_APP_TEAMSFX_ENDPOINT`
- `REACT_APP_FUNC_NAME`
- `REACT_APP_API_SCOPE` (only in `env/.env.dev`)
- the whole `STATE__FX_RESOURCE_SIMPLE_AUTH__*` and `PROVISIONOUTPUT__SIMPLEAUTHOUTPUT__*` family, plus `templates/azure/provision/simpleAuth.bicep` and `templates/azure/teamsFx/simpleAuth.bicep` (TeamsFx Simple Auth is a retired component)

Do not spend time filling these in when you set up a new environment.

## 4. Local setup for a new developer

Prerequisites: the Node version from `.nvmrc`, the Teams Toolkit VS Code extension (or `@microsoft/teamsfx-cli`), Azure Functions Core Tools v4, the .NET SDK, and an account on the dev tenant with permission to create an AAD app and a Teams app.

1. **Clone and install**
   1.1 `nvm use`
   1.2 `npm run installAll` (installs `tabs/` and `api/` dependencies)

2. **Provision the local environment**
   2.1 In VS Code, run the `Debug (Edge)` or `Debug (Chrome)` launch configuration, or run the `prepare local environment` task. Under the hood this runs `teamsfx provision --env local` and `teamsfx deploy --env local` against [teamsapp.local.yml](/home/mihai.nicolae/projects/edw/eea/eionet2-dashboard/teamsapp.local.yml).
   2.2 This creates a personal AAD app plus a personal Teams app, trusts a localhost dev certificate, and generates:
   - `env/.env.local` and `env/.env.local.user` (the secret is stored encrypted, `crypto_...`)
   - `tabs/.env.teamsfx.local`
   - `api/.env.teamsfx.local` (with `M365_CLIENT_SECRET` in **plaintext**)

3. **Fill in the values the toolkit does not generate**
   The generated files only cover identity and endpoints. Add by hand to `tabs/.env.teamsfx.local`:
   3.1 `REACT_APP_SHAREPOINT_SITE_ID`
   3.2 `REACT_APP_CONFIGURATION_LIST_ID`
   3.3 `REACT_APP_INSIGHTS_CONNECTION` (optional locally)
   And to `api/.env.teamsfx.local`:
   3.4 `REACT_APP_REPORTNET3_KEY` (only needed if you work on the reporting tab)
   Ask a team member for the current dev values, or copy them from `env/.env.dev` if you have it. Never commit them.

4. **Run**
   4.1 Frontend: `cd tabs && npm run dev:teamsfx` (this is `env-cmd -f .env.teamsfx.local npm run start`; plain `npm run start` gets no configuration and will not work)
   4.2 Backend: `cd api && npm run dev:teamsfx`
   4.3 Or just press F5 in VS Code, which starts both plus the Teams client.

5. **Common failure modes**
   5.1 API returns 500 `Missing required M365_* configuration for OBO.` → `api/.env.teamsfx.local` is missing or you started the API with plain `npm run dev`.
   5.2 Grids are empty and the console shows 404s from Graph → `REACT_APP_SHAREPOINT_SITE_ID` or `REACT_APP_CONFIGURATION_LIST_ID` is not set (step 3).
   5.3 Browser refuses `https://localhost:53000` → the dev certificate was not trusted; re-run the `prepare local environment` task, and check that `SSL_CRT_FILE` / `SSL_KEY_FILE` in `tabs/.env.teamsfx.local` point to files that exist.
   5.4 Values in `env/.env.local` such as `SSL_CRT_FILE`, `DOTNET_PATH` and the Simple Auth path contain **absolute paths of the machine that generated them**. Never reuse someone else's `env/.env.local`; regenerate your own.

## 5. Deploying to `dev` and `Prod_EEA`

Two build paths exist, and they read configuration from different files. This matters.

1. **Toolkit path (the normal one)**
   `teamsfx provision --env <envName>` then `teamsfx deploy --env <envName>`, driven by [teamsapp.yml](/home/mihai.nicolae/projects/edw/eea/eionet2-dashboard/teamsapp.yml).
   1.1 Configuration comes from `env/.env.<envName>` and `env/.env.<envName>.user`.
   1.2 The `build tab app` step explicitly forwards `REACT_APP_CLIENT_ID`, `REACT_APP_START_LOGIN_PAGE_URL`, `REACT_APP_FUNC_ENDPOINT` and `REACT_APP_FUNC_NAME`; the remaining `REACT_APP_*` values are picked up from the process environment loaded from `env/.env.<envName>`.
   1.3 It builds `tabs/`, uploads it to the Azure Storage static website, builds and zip-deploys `api/`, and updates the Teams app package.

2. **npm path (frontend only)**
   `cd tabs && npm run build:teamsfx:dev`, which is `env-cmd -f .env.teamsfx.dev npm run build`.
   2.1 Configuration comes from `tabs/.env.teamsfx.<envName>` only. `env/` is not consulted.
   2.2 There is no `build:teamsfx:Prod_EEA` script; a production build through this path needs `TEAMS_FX_ENV=Prod_EEA npm run build:teamsfx`.

3. **The two paths can and do disagree.** Today `env/.env.Prod_EEA` contains `REACT_APP_INSIGHTS_CONNECTION` while `tabs/.env.teamsfx.Prod_EEA` does not, so a production bundle built through the npm path ships without telemetry. Whenever you change an application variable, change it in **both** files for that environment.

4. Jenkins ([Jenkinsfile](/home/mihai.nicolae/projects/edw/eea/eionet2-dashboard/Jenkinsfile)) only runs release tagging, lint, unit tests and SonarQube. It performs **no** provisioning or deployment and needs no env files, which is why `yarn test` and `yarn run lint` work on a bare clone.

## 6. Secrets

1. `env/.env.<envName>.user` holds `SECRET_AAD_APP_CLIENT_SECRET` **encrypted** by the Teams Toolkit (`crypto_...`). The decryption key lives in the toolkit's per-machine store, so these files are only usable on the machine that created them. They are gitignored and were never committed.
2. `api/.env.teamsfx.local` holds `M365_CLIENT_SECRET` in **plaintext**. It is gitignored and has never been tracked in git. Treat it as a live credential.
3. `env/.env.dev`, `env/.env.Prod_EEA`, `tabs/.env.teamsfx.dev` and `tabs/.env.teamsfx.Prod_EEA` **were** tracked in git until recently and were removed in commits `1817313`, `c1c4f6a`, `e743c98` and `13887e0`. Their contents (tenant and subscription ids, resource ids, App Insights instrumentation keys) remain reachable in the git history. No plaintext client secret was ever committed, but the App Insights keys in history should be considered exposed.
4. In the cloud, secrets live in Function App application settings, set either by `arm/deploy` from `templates/azure/azure.parameters.<envName>.json` or manually (see 3.3).
5. Never commit an env file. If you need to share values, use the team's secret store, not the repository.

## 7. Where each variable lives, at a glance

```
env/.env.<envName>            toolkit state + provision outputs + application REACT_APP_* values
env/.env.<envName>.user       encrypted AAD client secret, TEAMS_APP_UPDATE_TIME
tabs/.env.teamsfx.<envName>   CRA build-time values (duplicate of the REACT_APP_* above)
api/.env.teamsfx.local        local Functions runtime values, plaintext client secret
api/local.settings.json       Functions host settings for local runs
templates/azure/azure.parameters.<envName>.json
                              resourceBaseName + AAD parameters passed to the bicep templates
templates/azure/teamsFx/function.bicep
                              the Function App application settings created in Azure
```
